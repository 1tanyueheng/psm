## Finished the "remove the title defence" refactor (backend + frontend)

The previous session had left this **half-done and the app fatally broken**. The
services and models were rewritten, but the wiring still pointed at deleted
classes. Finished it end-to-end.

### The target flow (now implemented)

```
Lampiran A   three candidate titles     student → supervisor
Proposal review  panel decides          supervisor acknowledges; panel records
  ├ approved            → Lampiran B
  ├ conditional_approve → Lampiran C → Lampiran B
  └ rejected            → another candidate title → supervisor re-acknowledges
Lampiran B   register the confirmed title → project created
```

**The title-defence sitting is gone.** `title_defences` and
`title_defence_sessions` are dropped, and the migrations that created/altered them
were deleted (with their `migrations` rows removed). The review now lives on
`supervisor_agreements` (`panel_decision`, `confirmed_title`, `panel_reason`,
`panel_comments`, `project_type/area`, `panel_1_name/2_name`, `panel_decided_at/by`,
`attempt`, `corrections_*`, `resubmitted_at`). The coordinator's JKPSM approval
step was removed too — the panel's verdict is final.

### What was broken when I picked it up

- `RegistrationController` imported the deleted `App\Enums\TitleDefenceResolution`
  → fatal on load.
- `SemesterService` imported the deleted `App\Models\TitleDefenceSession` and
  called `$semester->titleDefenceSessions()` (relation also removed).
- `AssignmentController` imported `TitleDefenceSession` and took a
  `title_defence_session_id` filter.
- `routes/api.php` still imported/registered `TitleDefenceController` (deleted).
- `SupervisorAgreementResource` referenced `resolvedDefence()`,
  `isDefenceGoverned()` and `STATUS_PENDING_JKPSM` — all gone. **And the resource
  was orphaned**: the controller returned `$agreement->toArray()`, so the resource
  was never used. I wired it in properly (list + show) and updated the two
  frontend pages to its shape (`student.name`, `supervisor.name`).
- The controller also called `$registrations->approve()/reject()`, which no longer
  exist.

### Key lesson (now in the verify skill)

**`php -l` passes on a file that imports a deleted class.** Lint parses syntax; it
does not autoload. So a half-finished refactor lints 100% clean and dies at
runtime. Detection order: list the classes → grep `app/ routes/ database/ config/`
for dangling names → `php artisan route:list` (routes referencing a deleted
controller are only strings, so they don't fail at boot) → exercise the paths.

## Session 2 — the title decision moved onto the PROPOSAL MILESTONE

The user changed direction again: *"the title defense no need [to be] started by
the coordinator, it is plant into the proposal milestone of student."* The
registration plan is explicitly abandoned. §10 of
`docs/REGISTRATION-FLOW-PLAN.md` records this; it supersedes §9.

### The flow now

```
Lampiran A → supervisor acknowledges (pairing registered, agreed title fixed)
Lampiran B → project created, milestone chain instantiated
PROPOSAL MILESTONE (sequence 1, code 'proposal') = the title decision
  student files the proposal, the SEATED PANEL rules:
    approved            → milestone approved → activateNext() opens the rest
    conditional_approve → student files Lampiran C → approved → the rest opens
    rejected            → student changes the title (written to projects.title)
                          → milestone reopens → re-file → re-decide
```

Four decisions confirmed with the user before building: the **panel** (2
examiners) decides; the student **uploads the proposal document** first; a
rejection means **edit the title then re-review**; the conditional document is
the **Lampiran C form** (comment/action rows + new title).

### Design choices worth keeping

- **The panel's verdict IS the milestone status.** No `panel_decision` column —
  `approved` / `conditional_approve` / `rejected` on `milestones.status`, with the
  reason in the existing `review_comment` and the author in `reviewed_by`. Only
  the Lampiran C columns had to be added. Much smaller migration than expected.
- **`MilestoneStatus::Conditional` is new** and deliberately distinct from
  `rejected`: a rejection means the *title* is wrong, a conditional approval means
  the title stands and the surrounding work needs fixing.
- **`approve()`/`requestRevision()` refuse the proposal milestone**, pointing at
  the decision endpoint, so the milestone cannot be fixed without the title ever
  being decided.
- **Changing the title writes `projects.title`** — the project title *is* the
  confirmed title.

### Three real bugs found (all pre-existing, all exposed by this change)

1. **`projects.agreement_id` was never written.** `submitTitleProposal()` recorded
   the agreement only in `metadata->agreement_id`, so `Project::agreement()` and
   `SupervisorAgreement::project()` resolved to **null for every project
   registered through Lampiran B** — the registration list could not link to the
   project. Fixed by writing the column; the migration backfills rows that only
   had the metadata key.
2. **`activateNext()` stalled the chain.** It only selected `pending` successors,
   so a chapter whose deadline passed while the proposal was still being decided
   was flipped to `overdue` by `flagOverdue()` (which includes `Pending`) and then
   skipped forever. The proposal gate makes this likely, not theoretical. Now
   selects the next `pending`/`overdue`/`rejected` milestone.
3. **Panel checks keyed on the role instead of the allocation.** The panel is
   drawn from `['examiner', 'supervisor']` (`ExaminerPairingService`), and the
   seeded pairs are **supervisors** — so `isExaminer()` locked the real panel off
   the milestone entirely: they could not even read it, because
   `ProjectPolicy::view` sent a supervisor down the `supervises()` branch. Fixed
   in `MilestonePolicy::isSeatedPanel()`, `ProjectPolicy::view()` **and**
   `Project::scopeVisibleTo()` (which must agree with the policy). **This is the
   lesson of the session:** my first HTTP check passed only because I happened to
   log in as `examiner@psm.test`, a genuine examiner; the *seeded* panel was
   supervisors. Always exercise the real fixtures, not a convenient actor.

### Session 4 — "the demo accounts can't see their project on /student/dashboard"

**Real bug, and a good one: `projects.academic_semester_id` was NULL for every
project registered through Lampiran B.**

`ProjectController::store()` and `ProgressionService` both set it;
`RegistrationService::submitTitleProposal()` was the **only** creation path that
did not. `ProjectSeeder` force-fills it for the 22 demo projects, which is exactly
why nobody had noticed — the only projects anyone looked at were the ones that
happened to be fine.

Why it blanked the dashboard: `ProjectController::index()` resolves an absent
`semester_id` filter to the **current term** (`AcademicSemester::resolveFilterId`)
and then applies `forSemester()`, which is `where('academic_semester_id', ?)`. A
null term matches no term, so `GET /projects` returned **0 rows** — the student's
own dashboard showed nothing. Confirmed: `total: 0` for `rd.student4` before,
`total: 1` after.

**Fix:** the term is now stored on the agreement and copied onto the project.

- New migration `2026_10_08_000002_stamp_the_term_on_lampiran_b_projects.php`:
  adds `supervisor_agreements.academic_semester_id` and backfills both tables
  (agreements from the session string, preferring the **active** term; projects
  from their agreement).
- `submitAgreement()` stamps `$semester->id` from `assertRegistrationOpen()`.
- `submitTitleProposal()` sets the project's term from the agreement, falling back
  to `resolveFilterId($agreement->session)` for legacy rows.
- `SupervisorAgreement` gained `academicSemester()` + the fillable entry.

**Why on the agreement:** `session` is only the session string ("2025/2026"), and
the faculty runs **two terms per session** — so it cannot identify the term.
`assertRegistrationOpen()` knows the exact term, so storing it there is precise.

Verified: fresh `migrate:fresh --seed` gives all four Lampiran B projects
`academic_semester_id = 2`, all four students get `total: 1` from `/projects`, the
dashboard's milestone call returns the chain, the seated chair still reads the
awaiting proposal with `can_decide_title: true`, and both checkers stay clean.

**Pattern worth remembering:** when a column is force-filled by the seeder but
never written by one of the app's own creation paths, the seeder hides the bug.
Grep for the column across *all* creators when a "nothing shows up" report comes
in.

### Session 5 — "the semester closed can't reopen"

**Closing a term was a one-way door.** `SemesterService::close()` existed with no
counterpart: no `reopen()` in the service, no route, and — because the UI rendered
the Close button only when `!row.is_closed` — no control at all once a term was
closed. An accidental close was unrecoverable without touching the database.

Note what `isClosed()` actually is:

```php
return $this->closed_at !== null || ! $this->is_active;
```

So a term that is merely *inactive* also reads as closed. The two seeded inactive
terms (1 and 3) therefore showed the "Closed" badge and **no action button
whatsoever** — which is exactly the dead end reported.

**Fix — `POST /semesters/{id}/reopen`**, mirroring `close`:

- `SemesterService::reopen()` — restores `is_active = true`, clears `closed_at`,
  runs `deactivateOthers()` (a faculty has exactly one live term), and logs the
  new `AuditAction::SemesterReopened`.
- Guard mirrors `isClosed()` exactly: `is_active && closed_at === null` → 422.
- `SemesterPolicy::reopen` (same audience as `close` — whoever can shut a term
  must be able to undo it) + `SemesterController::reopen` + the route.
- `semesterApi.reopen(id)` + a "Reopen term" button replacing the button that
  used to vanish.

**Design decision:** reopening restores the term as *live* but leaves
**registration closed**. `close()` does not record whether registration had been
open, so restoring it would be a guess — and guessing "open" would silently
reopen Lampiran A for a term the faculty may have deliberately stopped accepting
registrations on. The response message and the UI both say so, and the Open
button is in the next column.

Verified over HTTP: close → reopen on term 3 (`is_active` true, `is_closed`
false, and the previously-active term deactivated), a second reopen → 422, and the
audit trail records both transitions. The user's own browser confirmed it live
(Vite HMR) — the audit shows them closing and reopening Semester II at
01:46:53–55. Their close→reopen left registration closed as designed, so I
re-opened registration on term 2 to restore the demo.

**Pattern:** every lifecycle action needs a counterpart. `close` without `reopen`
is the same shape as the earlier "a closed defence sitting could never be
reopened" bug — and both were invisible because the UI simply hid the control
rather than failing loudly.

### Session 6 — design: admin adds a user with any role

Asked to **design** (not build) the admin add-user flow. Wrote
`docs/ADD-USER-DESIGN.md`.

**The API already exists and is role-aware** — `POST /api/users`
(`UserController::store`): admin-only (`UserPolicy::create`), `role` validated
against `Role::values()`, profiles created via `match ($user->role)`, random
password + `must_change_password` + `Password::sendResetLink`, audit. **The gap is
the screen**: `UserListPage.jsx` is filter-and-table only, with no `userApi.create`
call anywhere.

Six gaps found while grounding the design — the first two are real bugs:

1. **G1 — examiners get no profile.** `store()` covers Student / Supervisor /
   Coordinator, then `default => null`, so `Role::Examiner` creates a bare user
   with **no `staff_no`, no `can_examine`, no expertise**. Every *seeded* examiner
   has a `SupervisorProfile` (the seeder even comments "Examiners need a supervisor
   profile for staff_no and expertise"). Seeder-hides-the-bug again.
2. **G2 — a new student has no enrolment term.** `store()` never sets
   `student_profiles.academic_semester_id`, and `AssignmentService::assignSupervisor()`
   scopes its capacity gate by exactly that column (`assertPartCapacity($supervisor,
   $part, $student->academic_semester_id)`). Same class of bug as the Lampiran B
   semester omission.
3. **G3 — a soft-deleted user blocks their email forever.** `User` uses
   `SoftDeletes` but validation is `unique:users,email`, which counts trashed rows.
4. **G4 — `can_examine` is decorative.** Stored, cast, exposed, shown on the
   profile page — and **no query reads it**. `ExaminerPairingService::eligibleExaminers()`
   selects by role alone, so `can_examine = false` is still seatable.
5. **G5 — password delivery is a single point of failure.** The generated password
   is never shown and the account is reachable only by the set-password email; with
   no mailer the account is created *and unusable*, behind a 201 that looks fine.
6. **G6 — two staff identifiers.** `users.staff_id` and
   `supervisor_profiles.staff_no` hold the same value (the seeder sets both); the
   form would have to ask twice and they could disagree.

The doc carries the full role→field matrix, the API contract, the UI sketch
(inline panel — the UI kit has no modal), the test plan, and phasing.
**Not implemented** — awaiting the user's go-ahead.

### Session 7 — the two decisions, implemented

The user settled the two open questions and asked for them now:

**1. `can_examine` is dropped, not wired up.**
`2026_10_08_000003_drop_can_examine_from_supervisor_profiles` (round-trip tested).
Removed from `SupervisorProfile` (fillable + cast), `SupervisorProfileResource`,
`ProfilePage.jsx` and `UserSeeder`. Rationale recorded: whether someone may
examine is already expressed by their **role** and by the coordinator's seating
decision, so the flag only added a way to be surprised — it promised a
restriction no query enforced.

Followed the precedent in `2026_10_04_000001_remove_grade_concept`: **the create
migration is left untouched** and a new migration drops the column, so a fresh
install builds the schema in order and removes it at the end. (Unlike the
title-defence *tables*, where the create migration was deleted — for one column,
editing committed history buys nothing.)

**2. New accounts start on `password`.**
`config('psm.default_user_password')` = `env('PSM_DEFAULT_PASSWORD', 'password')`.
`UserController::store()` now: `Hash::make(config(...))` instead of
`bcrypt(Str::random(32))`, **no `Password::sendResetLink()`**, and
**`must_change_password = false`**.

Why false: `ForcePasswordChange` answers 409 on every route but the change form,
so flagging it would bar the new account from the system entirely — the opposite
of "sign in and reset later", which is the whole point of the user's reasoning
(the admin only holds the address; the holder resets when they want).

Trade-off stated in the design doc: anyone knowing an address can sign in until
that person changes their password. Acceptable for institutional addresses here;
flip `must_change_password` back to `true` for first-login rotation.

Also removed a pre-existing unused `NotificationType` import from
`UserController`.

**Verified:** migration `up`/`down` round-trip; fresh `migrate:fresh --seed` (47
steps) leaves no `can_examine` column and all 4 seeded examiners still have a

### Session 9 — the coordinator's panel-pairing screen

The user reported the assigned examiner "disappearing" and asked for a pairing
system where the coordinator gives a student a pair of examiners, excluding the
student's own supervisor.

**The finding: the coordinator never had a screen for it.** `/assignments` has two
tabs — *Assign* (supervisor) and *Current pairings* (supervision pairs) — and
nothing about the panel. The examiner endpoints
(`/assignments/examiners`, `/assignments/examiner-pairs`) existed in
`endpoints.js` but **no page called them**. So the panel was real and stored, and
visible to the student/supervisor on the project page
(`ProjectResource.examiners`), but invisible to the coordinator who seats it —
which reads as "the examiner disappeared".

**Built:**

- `AssignmentService::assignExaminerToStudent()` — the examiner rules anchored on
  the **student** rather than the project, because a panel must exist before the
  project does (it rules on the title at the proposal milestone). `project_id` is
  stamped when one already exists, and by `submitTitleProposal()` otherwise. The
  project-shaped `assignExaminer()` now **delegates** to it, so there is one
  implementation of the conflict-of-interest / duplicate / panel-cap rules; it
  keeps its extra check over co-members, since the panel is seated per student.
- `ExaminerPairingService::panelCandidates($student, $psmPart)` — the pool minus
  the student's own supervisor(s) and anyone already seated.
- `ExaminerPairingService::assignPair($student, [chair, member], $actor, $psmPart)`
  — retires the previous panel first (so re-pairing **replaces** rather than being
  refused by the cap), then fills both seats through `assignExaminerToStudent()`.
- `GET|POST /assignments/students/{student}/panel` (`showPanel` / `storePanel`),
  with `resolvePanelPart()` defaulting the batch from the student's own project.
- `frontend/src/pages/assignments/PanelAssignmentPage.jsx` at
  `/assignments/panels`, plus a menu entry under Cohort. It names the excluded
  supervisors explicitly, seeds the pickers from the current panel, and filters
  each picker against the other so the same person cannot be picked twice.

**Decisions worth keeping:** a panel is a *pair against a student*; the first id
is the **chair**; capacity is never consulted (it limits supervising, not
examining); retired allocations are kept inactive rather than deleted so the audit
trail survives.

### Session 10 — two silent regressions from the role merge, and the panel's other job

Docker came up; the outstanding verification passed (lint, routes, the panel
endpoints, the conflict-of-interest refusal). Then the user reported
`/milestones/1` showing **no panel**, which turned out to be two real bugs I had

**1. `EvaluationSeeder`'s panel pool went empty.**
