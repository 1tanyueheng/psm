   session string ("2025/2026"). They are *different* columns of

   - `check_seeders.py`: 4 problems — `AcademicSemester` fillable vs schema

## Session 2 — the app actually runs in Docker, so I could verify for real

The reported error was `Unknown column 'attempt' in 'order clause'` on the title
defence page. Cause: the migration had never run. `psm-app` had been up 7 hours
and this project only migrates **at container start**
(`docker/supervisord.conf` → `[program:migrate]`, `autostart = true`,
`autorestart = false`, guarded by `RUN_MIGRATIONS`). A container that predates a
new migration file keeps the old schema.

### How to run/verify here (no PHP on the host, but Docker is available)
```bash
docker ps                                              # psm-app, psm-db, psm-mailpit, psm-frontend
docker exec psm-app php artisan migrate --force
docker exec psm-db mysql -upsm -psecret -N -B psm_system -e "SHOW COLUMNS FROM title_defences;"
docker exec -i psm-app php <<'PHP' ... PHP             # pipe a script straight into php
```
Behaviour was verified by running the whole flow inside
`DB::beginTransaction()` … `DB::rollBack()` — 24 assertions, no data written.
This is now the way to test here; there is no test suite (`backend/tests` absent).

### Three real bugs found by that verification
1. **MySQL error 1553 — cannot drop an index needed by a foreign key.**
   `defence_session_student_unique` was the only index whose leftmost column was
   `title_defence_session_id`, so InnoDB refused to drop it while the sitting's FK
   existed. Same trap later on `examiner_unique_per_student` for
   `student_profile_id`. Fix: **drop the FK first, swap the index, restore the
   FK** — in both `up()` and `down()`. DDL is not transactional on MySQL, so a
   half-failed migration leaves the FK already gone: every drop must be guarded
   (`dropForeignIfExists()` checks `information_schema.KEY_COLUMN_USAGE`).
   `examiner_assignments.project_id` has no index of its own either — InnoDB
   serves it with `examiner_unique_per_part`, same arrangement.
2. **`supervisor_agreements.session` stored the term *name*, not the session
   string.** `RegistrationService::submitAgreement()` wrote `$semester->name`
   ("2025/2026 Semester II") while projects and sittings use
   `$semester->academic_session` ("2025/2026"). `Project::nextCode()` counts
   within `(psm_part, academic_session)`, so a Lampiran B in a term with existing
   projects counted zero and generated an already-taken code →
   `1062 Duplicate entry 'PSM1-2025-CS2-001'`. Fixed in the service plus
   migration `2026_10_06_000002` (idempotent JOIN-style normalisation; `down()`
   is deliberately a no-op because two terms share one session string).
3. **A relation's built-in `orderBy` silently wins over an appended descending
   one.** `SupervisorAgreement::defences()` carries `orderBy('attempt')`;
   `resolvedDefence()` appended `orderByDesc('attempt')`, producing
   `ORDER BY attempt ASC, attempt DESC, id DESC` — the ascending clause wins, so
   it returned the *first* attempt. A successful re-defence was still refused for
   the original rejection. Fix: `->reorder()->orderByDesc(...)`. **Watch for this
   pattern anywhere a relation has a baked-in order.**

## Session 4 — two active semesters, and a demo cohort for the defence

### Why two semesters were active
Both `2025/2026 Semester I` and `Semester II` had `is_active = 1`. The app
forbids this: `SemesterService::create()` and `update()` both call
`deactivateOthers()`, and `AcademicSemester`'s docblock states the invariant.

The audit trail is what settled it. The only semester entries ever recorded are
`semester.grades_released` (id 230), two `PATCH /api/semesters/2` and two
`POST /api/semesters/2/close` at 15:29:54–55 (ids 301–304), and a grades
release/withhold on term 3. **No entry activates any term.** Also, `close()` sets
`is_active = false` *and* `closed_at`, while re-activating clears `closed_at` — so
`Semester II` having `closed_at` set *and* `is_active = 1` cannot be produced by
the API at all. The flags were changed outside the app (phpMyAdmin is exposed on
:8081, or manual SQL). The audit rows are also doubled, and the term was renamed
to "Renamed" then restored with no audit entry — more signs of direct edits.

Fix: `SemesterService::update($term, ['is_active' => true, 'is_registration_open'
=> true], $admin)` — the service path, so `deactivateOthers()` runs. Exactly one
active term now.

## Session 6 — is there a PSM 1 → PSM 2 progression? No.

Asked: how does a PSM 1 student move to PSM 2 after the marks are released?

**There is no progression feature.** Evidence:
- `config/psm.php` declares `progression_term_gap` with a docblock about "PSM 1 →
  PSM 2 progression", and **nothing anywhere reads it**. Dead config for a
  feature that was never built.
- `SemesterService::setMarkRelease()` only stamps `FinalGrade.released_at` and the
  term's flags. It touches no student.
- No endpoint, service method or UI promotes a student. **No app code writes
  `student_profiles.academic_semester_id`** — only `ProjectSeeder` force-fills it
  for the demo.
- `docs/REQUIREMENT_TWO_BATCHES_SAME_SEMESTER.md` §6.2 was *corrected* to allow a
  student to hold PSM 1 and PSM 2 in the same term, which de-emphasised
  progression as a distinct event.

**What actually happens** (verified end-to-end in a rolled-back transaction):
1. Coordinator activates the next term and opens registration.
2. Student files a **new Lampiran A** with `psm_part = PSM2`.
3. Supervisor acknowledges, JKPSM approves → a *second* supervision assignment;
   the student then holds PSM1 **and** PSM2.
4. Per the earlier decision, PSM 2 inherits the PSM 1 title → no second defence →
   Lampiran B → PSM 2 project.
5. The PSM 1 project is archived separately and manually — `POST
   /projects/{id}/archive`, or `ArchiveService::archiveBatch($batch, $actor,
   $psmPart)` which only picks up `status = completed` projects.

### The bug this exposes
The student's `academic_semester_id` **never advances**, and
`AssignmentService::assignSupervisor()` scopes the capacity gate by exactly that
column: `assertPartCapacity($supervisor, $part, $student->academic_semester_id)`.

So a PSM 2 registration in a *later* term is capacity-checked against the
student's *earlier* term. Demonstrated with one supervisor, one part, one
capacity:

| term passed to the check | PSM1 load | `hasCapacityForInSemester('PSM1', …)` |
|---|---|---|
| 2025/2026 Semester II | 2 | **false** (refused) |
| 2026/2027 Semester I | 0 | **true** (allowed) |

Capacity is 2, so the same supervisor is simultaneously full and not full
depending only on which term is passed. A supervisor already at their cap in the
new term would still accept a progressing student, because the gate measured the
old term — and the reverse refusal is just as wrong.

Related: `SemesterService::currentFor($student)` returns the student's own term
when it is active, else the faculty's. With a stale enrolment, a student who has
progressed is handed their old term as the default on every term-scoped screen.

**Not fixed — it is a design decision.** Two options: (a) an explicit progression
step that advances `academic_semester_id` (and optionally archives the PSM 1
project) — what the requirement doc's "progression target" implies; or (b) pass
the term being registered *into* into `assertPartCapacity` instead of the
student's enrolment. (b) is the smaller fix and does not depend on anyone
remembering to advance a column.

## Session 7 — the user stated the real PSM 1 → PSM 2 rule

> Same title across both parts, two continuous semesters. **Only PSM 1 registers a
> title.** PSM 1 does Chapters 1–4, PSM 2 does Chapters 5–7.

Checked the system against each clause:

| Rule | System today | Verdict |
|---|---|---|
| One shared title | PSM 2 *can* inherit the PSM 1 title via `resolvedDefence()`, but nothing forces it | partial |
| Only PSM 1 registers a title | A PSM 2 Lampiran A with three new titles is accepted (demonstrated) | **diverges** |
| Two continuous semesters | `progression_term_gap` documented for exactly this, **never read**; no progression step | **not implemented** |
| PSM 1 = Ch 1–4 | proposal, ch1–ch4, final_report | matches |
| PSM 2 = Ch 5–7 | **ch4, ch5, ch6, ch7**, final_report | **diverges** |

**`chapter_4` is byte-identical in both chains** — same title, same weight (20),
same description, for both categories. So a student doing PSM 1 → PSM 2 on the
same title submits the *same* Chapter 4 milestone twice. `MilestoneTemplateSeeder`
documents this as deliberate ("Version 3 splits the chain by PSM part: PSM 1 runs
proposal + Chapters 1-4, PSM 2 runs Chapters 4-7"), so it is a considered design,
not a slip — it just disagrees with the rule the user stated.

**The UI already sides with the user.** `frontend/src/lib/psmPart.js:38` tells
students PSM 2 is *"Chapters 5–7 and the final report"*, while the milestone chain
delivers Chapters 4–7. So the frontend and the backend already contradict each
other.

Weights, for reference: PSM1 6 items = 100 (proposal 10, ch1 15, ch2 15, ch3 15,
ch4 20, final 25). PSM2 5 items = 100 (ch4 20, ch5 20, ch6 15, ch7 15, final 30).
Dropping ch4 from PSM 2 frees 20 that has to be redistributed — a faculty
weighting decision, so it was not invented.

Template changes go in as a new **version** (`resolveFor()` picks the highest
version for new projects; in-flight projects keep the chain they were given), so
this is additive rather than a rewrite.

## Session 9 — one batch-level action instead of two per-student buttons

Asked to remove the project page's **Add milestone** and **Create assessment**
buttons and make it one action for all students in the batch.

**Both buttons were dead links**, which is worth remembering as a pattern:

- `Add milestone` → `/projects/{id}/milestones/new`. No such route, and there is
  **no milestone-creation endpoint at all** — `MilestoneController` has no
  `store`; milestones exist only via `MilestoneService::instantiateFor()` from the
  template at registration. So the whole affordance was fictional.
- `Create assessment` → `/evaluations/new?project={id}`. That matches
  `/evaluations/:id` with `id = "new"`, so it rendered the evaluation form for an
  evaluation literally named "new".

**The frontend checker did not catch either**, and the reason matters: its link
rule only matches `to="..."` with double quotes. Both links use
`to={`...`}` template literals, which the regex never sees. **A checker blind spot
worth closing if more template-literal links appear.**

**The replacement** is a single **Open assessment window** action (coordinator/
admin, live projects) linking to `/assessment?semester_id=…&psm_part=…`, which is
genuinely the batch action: `AssessmentWindowService::open()` loops every project
in the window and calls `submissions->open($project, $studentId, $actor)` for
every student. Verified: one window for (2025/2026 Semester II, PSM1) allocated
**8 students × 3 forms = 24**, 0 failures.

`AssessmentWindowPage` now reads those query params: the list is filtered by the
scoped term and the matching batch's window is selected. It deliberately does
**not** auto-open the create form — a batch may only have one window per term
(`assessment_windows_term_part_unique` enforces it), so offering to create a
second would only offer an action that cannot succeed. The scoped values still
pre-fill the form.

Both checkers still clean. The `medalFor` warning in `lib/format.js` is the only
remaining item on either.
